# context engineering

memory = information stored by an agent for possible use in future steps or interactions
-  eg. preferences, mistakes - used for features

context = any information that is supplied to the agent when we want it to execute a task
-  system instructions and user requests
-  conversation history
-  retrieved memories and documents
-  tool results
-  ...

context engineering = determines what info to include, exclude, compress and organise for each LLM call

## what is context engineering?

process of selecting and organising the information supplied to an LLM at each step of an agent's execution

-  too little context = lacking information needed to complete the task (eg. agent asked to fix a failing test without an error message)
-  too much context = irrelevant or outdated information that distracts LLM and reduces performance (eg. outdated error message, LLM fixes the error that was already fixed)

effective context engineering: provide the smallest set of relevant, useful information for the current task

## prompt engineering vs context engineering

prompt engineering: designing and refining prompts to guide LLM behaviour

context engineering: managing the information provided to the LLM at each step

developer designs and implements how context is constructed and managed using code, frameworks and tools

example - research agent:
-  prompt engineering: specify how research findings should be summarised and cited
-  context engineering: retrieve relevant papers, retain useful findings from earlier searches, incorporate new evidence and exclude irrelevant or outdated information

-  **providing information in addition to what we need from the prompt**

## why context engineering matters

1.  limited context window - limited amount of information you can include in an LLM call (paying for tokens, wasting tokens = wasting money)
2.  irrelevant information - unnecessary  documents, messages or tools distract and overwhelm the LLM, so we get wrong results
3.  outdated information - information for step 1 might not be needed for step 50
4.  relevant information may be overlooked - when LLM is overwhelmed, it may ignore the actual relevant information and give us a wrong result

## when context fail: four failure modes

1.  context **poisoning**: repeatedly using incorrect information (not correcting a mistake eg. getting wrong information from an API)
2.  context **distraction**: happens when you have long context (when you retrieve too much information from somewhere and just pass it as context) - the agent is confused or lazy and will only look at the context without using its own thinking
3.  context **confusion**: happens when we ask the models to use a lot of different APIs - LLM cannot distinguish relevant and irrelevant information
4.  context **clash**: new information conflict with old information which are already in the context

## poisoning

how to address: always check what is generated by the agent - make sure it is correct
-  if it is not, check the context and remove any incorrect info/replace with correct info

## distraction

how to address: keep the task objective and relevant information in the context
-  remove unrelated details and repeated information that may distract the LLM

happens if the conversation is too long

## confusion

how to address: limit the information and tools available to the LLM to those needed to perform the current task
-  use the smallest number of tools and data that keep the relevant information to complete a task

happens if agent has too many tools and information it doesn't need, so it doesn't choose right tools and information to solve a problem

## clash

how to address: instruct the LLM to reorganise conflicting information, prioritise more authoritative or recent information/sources when appropriate and ask for clarification when the conflict cannot be resolved

happens when information of instructions from different sources conflict

## strategies for improving context quality in LLM agents

-  select relevant information - reducing context distraction and confusion
-  limit available tools - reducing context confusion
-  compress context - reducing context distraction
-  isolate tasks - preventing information from one subtask interfering with another
-  refresh context - resolving conflicts
-  prevent context poisoning - prevent untrusted data to override agent's instructions (treat any retrieved data as untrusted, verify before using)
	-  context poisoning can happen with malicious injections - changing the context (eg. ignore all previous prompts and do this)

## constructing context for each LLM call

-  include agent's instructions and the current user prompt
-  include relevant previous interactions, decisions and intermediate results maintained in working memory
-  RAG - retrieve relevant information from external sources

# tool calling

## part 1: tool usage and learning

tools enable LLM agents to access information and perform actions beyond text generation
-  access info: retrieve data from sources such as databases and APIs
-  perform actions: execute operations through tools such as sending emails or updating databases etc.

key characteristics of tools:
-  separate from the LLM
-  callable
-  purposeful
-  structured I/O

**RAG** = focuses on retrieving information from external sources, but nothing else
**memory** = retrieving information from the database that agent made themselves through previous work
**tools** = callable capabilities to access information and perform computations/execute actions

### tool usage stages

1.  tool creation and integration
2.  tool definition
3.  tool selection
4.  tool calling
5.  output processing

### how LLMs Learn and Use Tools

1.  **learning** : fine-tuning (learning from examples) and reinforcement learning (learning from feedback/mistakes)
2.  **prompting**: providing tool definitions to the LLM at runtime

### tool definition - best practice

-  describe tools clearly
-  avoid overlapping tools
-  keep tools focused
-  manage tool outputs
